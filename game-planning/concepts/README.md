# Game Planning — Concepts

Status: active game-planning direction owner
Scope: navigation and working boundaries for whole-game Concept ideation, analysis, comparison and validation.

## 1. Responsibility

Use this area when the planning object is **one possible whole game** or when several possible game Concepts are being compared.

Reusable routes:

- creation/synthesis: [`../../game-creation-workflow.md`](../../game-creation-workflow.md)
- detailed Concept review: [`../../game-analysis-reference/game-concept-analysis-and-planning.md`](../../game-analysis-reference/game-concept-analysis-and-planning.md)
- practical navigation: [`../../game-planning-use-case-map.md`](../../game-planning-use-case-map.md), Concept use case

A Concept is compact integration, not a copy of every detailed owner.

## 2. Workspaces

- [`ideas/README.md`](ideas/README.md) — possible whole-game Concepts and unresolved Concept-level questions before/around a specific Concept record.
- [`survivor-base.md`](survivor-base.md) — current working whole-game Concept record for Survivor Base.

Add another Concept record when a distinct whole-game possibility is useful to preserve/review independently.

## 3. Concept Versus Project Workspace

```text
concept record
  → compact whole-game thesis + cross-lens status/evidence;

concrete game workspace
  → detailed Scenarios, units, Experience, Visual, Marketing,
    project Ideas, evidence and migration sources.
```

For Survivor Base, detailed project work remains under [`../survivor-base/README.md`](../survivor-base/README.md).

## 4. Ideas Boundary

`concepts/ideas/` is for questions such as:

```text
What whole game could this seed become?
What alternative whole-game direction should be compared?
What major Concept transformation could solve the current problem?
```

A lower-level mechanic/Situation/visual/marketing question should normally live with its nearest affected owner instead.
