## 4. Expanded Pre-Play / Gameplay-Entry Detail

### P0 — First Contact / Virus-World Orientation

**Beat role:** pre-play orientation / presentation; not automatically gameplay.

**Relevant state BEFORE**

- the player has not yet entered the concrete Survivor Base gameplay chronology;
- the exact information the player already knows is not fixed here.

**What happens / causal work INSIDE**

The current selected responsibility is shallow orientation rather than deep exposition. It should communicate enough scale and character of the infection for the player to understand the world they are entering before local rules demand decisions.

The current Idea workspace preserves that the virus/world layer should make clear that infection is not only a bite mechanism and can spread through virus-like routes. Exact transmission routes and what is known about the current strain remain project/system questions; presentation must not invent a universal route merely to make the point.

The opening may hint that infection changed or behaved heterogeneously only when the supporting lore Variant is actually selected/reconciled.

**Presentation alternatives / unresolved work**

- [`OPEN-FIRST-P01`](../ideas/first-play-context-and-gameplay-entry/open-first-p01-initial-context.md) owns the current presentation alternatives, including `OPEN-FIRST-V01` and the affected-animal `OPEN-FIRST-V02`;
- this Spine does **not** select either Variant merely by referencing them.

**Relevant state AFTER / HANDOFF**

The player should have a sufficient high-level world model to receive the concrete game/base context without the pre-play layer claiming unsupported detailed rules.

## 5. Gameplay Beats — Detail Accumulation

The following sections intentionally preserve the selected backbone without inventing the concrete details that still need the next planning pass. Expand each Beat with the reusable Scenario record proportionally as those details become known.

### T0 — Newcomers Arrive / Are Detected

**Relevant state BEFORE:** existing base + clean trusted core; gameplay-entry player context must be explicit.

**INSIDE:** exact newcomer group, arrival/detection circumstances and first available information are open.

**AFTER / HANDOFF:** the group reaches a concrete intake problem.

### T1 — Intake

**BEFORE:** newcomers require processing before ordinary integration.

**INSIDE:** concrete intake Execution, information production, physical routing and constraints remain to be detailed from current project meaning/source context.

**AFTER / HANDOFF:** enough concrete state/information exists to produce an admission decision.

### T2 — Admission Decision

**BEFORE:** newcomer state, evidence, base needs/capacity and Player Context must be concrete enough to understand the decision.

**INSIDE:** preserve visible meaningful options, the selected Scenario branch and why this Player Context selects it. Do not choose the branch before those inputs are specified.

**AFTER / HANDOFF:** the selected decision creates the concrete integration/work state used by the next Beat.

### T3 — Integration / Work

**BEFORE:** admission decision has created a concrete status/access/work configuration.

**INSIDE:** show the selected consequences in routine operation rather than treating admission as an isolated gate decision.

**AFTER / HANDOFF:** observation, work and social contact can make the newcomers more known.

### T4 — People Become More Known

**BEFORE:** newcomers have lived/worked inside the chosen configuration.

**INSIDE:** concrete observations/reports/interactions change available information and beliefs.

**AFTER / HANDOFF:** later ambiguous evidence can be interpreted against a richer history rather than only the initial intake snapshot.

### T5 — Ambiguous Evidence

**BEFORE:** the base has an existing assessment/history for the person/group.

**INSIDE:** exact symptom, report, event or other evidence remains open; it must not be silently chosen here.

**AFTER / HANDOFF:** uncertainty becomes salient enough to require response before full certainty.

### T6 — Response

**BEFORE:** ambiguous evidence is actionable but incomplete.

**INSIDE:** exact response and selected branch remain open.

**AFTER / HANDOFF:** the response produces conditions/information for investigation.

### T7 — Investigation

**BEFORE:** a concrete response has constrained or exposed the problem.

**INSIDE:** exact evidence-production/information-combination path remains open.

**AFTER / HANDOFF:** enough new information exists for a stronger assessment.

### T8 — Assessment

**BEFORE:** earlier intake history + lived behavior + ambiguous evidence + investigation findings are available proportionally.

**INSIDE:** exact diagnosis/assessment outcome and consequent decision remain open.

**AFTER / HANDOFF:** the concrete case has produced a lesson/consequence capable of changing future operation.

### T9 — Persistent Procedure / Policy Change

**BEFORE:** the base has experienced the consequences of the selected newcomer path.

**INSIDE:** exact procedure/policy/operating adaptation remains open.

**AFTER / EXIT STATE:** the base remains operational but its future procedure/policy has changed because of this concrete case.
