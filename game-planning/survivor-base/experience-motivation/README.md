## 1. Responsibility

This area owns independently useful project-specific Experience / Motivation detail for Survivor Base when that responsibility is worth preserving in its own project owner.

Possible units when justified:

```text
Project Experience;
Project Motivation;
candidate Experience Promise;
candidate Doubt / Concern;
owner-local Ideas / Variants.
```

This README establishes working ownership/routing only. It does **not** populate concrete Survivor Base units automatically from the legacy Draft, and the existence of this owner does not promote any concrete unit or status.

## 2. Working Boundaries

```text
Project Experience
= concrete Survivor Base Experience being planned;

Project Motivation
= what player wants to seek/continue/preserve/resolve/avoid/validate;

Situation Goal
= concrete future result inside one decision;

Experience Promise
= candidate unit for how one Experience becomes expectable;

Doubt / Concern
= candidate unit for suspicion about unwanted/missing gameplay Experience.
```

Generic reusable `Player Promise` terminology does not create a mandatory project-local object here.

## 3. Availability Chain

```text
Experience Opportunity
→ Experience Legibility / Awareness
→ Experiential Expectation
→ Motivation.
```

These are working distinctions, not four mandatory file types.

## 4. Classification / Quality

A Project Experience may use 0..N reusable Experience-family classifications. Classification may be candidate/unresolved and is used as a **quality-analysis lens**, not only a tag.

The project-specific Experience remains the identity; reusable families supply specialized conditions/questions/reference knowledge/anti-patterns.

## 5. Motivation Relations

Keep `Meta / Experiential Motivation`, `In-Play Motivation` and concrete Situation Goal distinct.

A Motivation may link to Project Experiences/families, direction (`seek / deepen / preserve / restore / resolve / avoid / validate`), Goals/Strategies/Plans it tends to produce, Situations/Executions/Loops it makes salient, and Promise/Doubt when material.

Do not require symmetric desired + avoided Experience fields.

## 6. Negative / Aversive Boundary

```text
intended aversive in-game Experience/outcome
≠ anti-experience / design failure
≠ coherent gameplay disliked by this audience/genre preference.
```

A player can value serious consequences while being motivated to avoid them in-fiction.

## 7. Player Context / Expertise

Record only context relevant to a concrete Scenario/question; no full persona is required. Keep game-provided Information separate from prior/learned mental model/expertise.

Possible expertise dimensions: Rules Familiarity, Causal-Model Accuracy, Pattern Familiarity, Option Awareness, Strategic Repertoire, Execution Fluency, Content Familiarity.

## 8. Ideas / Variants / Files

Use normal owner-local Ideas. Do not pre-create empty folders merely to mirror ontology. Exact one-file/folder grammar remains provisional until real unit count/reuse is visible.

Use the reusable record templates proportionally and revise them after the planned `Spine Scenario ↔ low-level units` pass.
