# Game Concept Analysis And Planning

Status: active reusable detailed-planning method
Scope: how to inspect, plan and validate one possible whole game across existing gameplay, Experience, Visual, audience/market, reference and feasibility surfaces, then reconcile detailed evidence back into a compact Concept.

## 1. Purpose And Boundary

Use this method when the review object is the **whole-game Concept**, not only one Scenario, system or local design problem.

The creative synthesis route remains in [`../game-creation-workflow.md`](../game-creation-workflow.md). Stable meanings remain in principle owners. This file coordinates a Concept-level review across existing lenses and does not copy their full question sets.

```text
Concept
  = compact integrated representation of one possible whole game;

Concept analysis
  = inspect whether its major promises/responsibilities compose;

project detail owners
  = hold the actual detailed gameplay / Experience / Visual / Marketing / other meaning.
```

A Concept record is not a miniature duplicate of every project file.

## 2. Concept Record Surface

Use proportionally. Leave a section open when evidence/detail does not yet justify an answer.

```text
Concept identity / current status

Compact whole-game thesis
Player role / fantasy / promise
What the player mainly does
Broad Core Loop / recurrent activity thesis
Key controlled/world entities and important state relations
Character of meaningful decisions
Long-term change / important Dynamics, when known

Target Player Experience / Motivation thesis
Visual identity / readability thesis
Audience / purchase fantasy / comparison set
Market legibility / differentiator / proof requirement
Reference baseline / transformation thesis
Production / technical / content feasibility
Representative Scenario / Spine evidence

Main contradictions / risks / unknowns
Evidence that can change the Concept
Current review conclusion / next Concept-changing question
```

These are discovery/review surfaces, not mandatory empty headings for every Concept file.

## 3. Lens Map

### Gameplay / Structure

Use [`game-structure-analysis.md`](game-structure-analysis.md) and gameplay-planning owners when needed.

Ask proportionally:

- What does the player repeatedly do and decide?
- What states/resources/actors make those decisions meaningful?
- What changes over a session/campaign?
- Does the broad Core Loop describe real recurrent play rather than only a pitch sentence?
- Which systems are load-bearing versus supporting?

### Player Experience / Motivation

Use [`player-experience-and-anti-experience.md`](player-experience-and-anti-experience.md) and [`player-experience-motivation-planning.md`](player-experience-motivation-planning.md).

Ask:

- What Experience is the game trying to create repeatedly?
- What makes the player want to pursue its activities?
- Which anti-experiences could break the promise?
- Does detailed gameplay actually create the intended Experience?

### Visual

Use [`visual-design-analysis-and-planning.md`](visual-design-analysis-and-planning.md) and the relevant visual principle owner.

Ask:

- What must be readable for the central decisions to work?
- What visual identity supports the intended fantasy/Experience?
- Can the Concept's important information and states be communicated credibly?
- What visual/asset burden is implied by the promise?

### Audience / Marketing

Use [`../principles/audience-is-part-of-the-game-principles-and-terminology.md`](../principles/audience-is-part-of-the-game-principles-and-terminology.md) and [`../principles/market-and-platforms-principles-and-terminology.md`](../principles/market-and-platforms-principles-and-terminology.md).

Ask:

- Who is this for?
- What purchase fantasy should become legible quickly?
- What games form the useful comparison set?
- Why choose this game instead?
- What screenshots/trailer/demo/playable proof can demonstrate the real promise?
- Does positioning create expectations the actual game can satisfy?

### References / Comparison

Use the active reference-first principles and concrete game analysis as evidence.

Ask:

- What existing games prove parts of this direction can work?
- Which causal responsibilities are being borrowed?
- What is transformed rather than copied?
- Which comparison is useful for design, audience legibility or production feasibility?

### Production / Feasibility

Ask:

- What system/content/art/technical depth is required before the central value appears?
- What dependencies can block a credible proof?
- Can a representative slice demonstrate the Concept without pretending to prove the entire final production?

## 4. Representative Scenario / Spine As Concept Evidence

A Concept can look coherent at high level and still fail when made concrete. Use representative Scenarios/Spines to expose the actual decisions, processes, information, pacing, Experience and presentation burden.

```text
Concept
→ representative selected Spine
→ detailed concrete local units inside the Spine
→ Low-Level Elements / scoped Ideas
→ reusable owners where independent responsibility emerges
→ cross-lens evidence
→ Concept review / revision.
```

The Scenario proof should not stop at Beat names when those names hide the design question. For each material local Situation, Event, Execution, Loop manifestation or other low-level unit, use the **applicable fields of its detailed method for that concrete Scenario/run**.

```text
Scenario-local unit detail
  = what this unit is HERE;

reusable unit owner
  = what this responsibility can be across Scenarios/configurations.
```

A reusable owner is not required before detailed local planning is allowed. Conversely, one richly detailed occurrence does not establish the whole reusable possibility-space.

## 5. End-To-End Concept Validation Pass

Use when uncertainty in the whole-game direction is high enough to justify a representative deep pass:

```text
state current Concept
→ identify the most load-bearing cross-lens unknowns
→ choose representative Scenario / Spine proof
→ make chronology concrete end to end
→ detail material local units proportionally
→ record Experience / Visual / Marketing / feasibility implications
→ extract reusable owners only where useful
→ return evidence to Concept
→ deliberately retain / revise / transform / reject affected meaning.
```

Completing one representative Spine does not prove every future playthrough or every whole-game Dynamic. Its purpose is to force enough concreteness that Concept assumptions can be inspected rather than protected by abstraction.

## 6. Concept Review Questions

At review, ask:

```text
Does the concrete game still match the compact thesis?
Which part of the original promise became stronger?
Which part disappeared when made concrete?
Which planned activity is actually carrying the Experience?
Which system now looks unnecessary?
Which previously hidden production burden became load-bearing?
Which visual/information requirement is harder than assumed?
Which audience/market promise is unsupported by actual play?
Which comparison/reference became more or less useful?
What would we change if we were free to revise the Concept now?
What evidence is still missing before confidence should increase?
```

## 7. Ideas And Alternatives

Concept-level uncertainty may route to [`../game-planning/concepts/ideas/README.md`](../game-planning/concepts/ideas/README.md) or another nearest owner-local Idea workspace.

Preserve:

```text
Concept Idea / Prompt / Idea Variant
  ≠ accepted whole-game Concept meaning;

one Concept Variant
  ≠ automatically selected game direction;

one detailed Scenario
  ≠ complete proof of the whole game.
```

## 8. Do Not

- Do not fill every lens mechanically before useful gameplay work can begin.
- Do not copy full Experience/Visual/Market methods into the Concept record.
- Do not let a Concept summary become a second owner of detailed project truth.
- Do not increase confidence merely because a large amount of documentation exists.
- Do not treat market positioning as a post-development wrapper disconnected from the actual game.
- Do not treat one representative Scenario as proof of every path or Dynamic.
