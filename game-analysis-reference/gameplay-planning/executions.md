# Gameplay Execution Planning

Status: working / provisional reusable detailed-planning method
Scope: independently useful action/process execution that unfolds through game time after/around decisions, rules and agents.

Canonical Gameplay Situation / Loop / Scenario terminology remains in [`Gameplay Situations, Loops And Scenarios — Principles And Terminology`](../../principles/gameplay-situations-loops-and-scenarios-principles-and-terminology.md). Domain ownership principles remain in [`Game Planning`](../../principles/game-planning-principles-and-terminology.md).

`Execution Unit` is **not yet a canonical fifth gameplay scale**.

## 1. Working Meaning

```text
Decision / Event / state condition
→ execution starts
→ intermediate work / movement / waiting
→ resources/capacity/state may change
→ information may appear
→ process completes / fails / is interrupted
→ later decision space changes.
```

Execution does not require a new meaningful decision at every moment.

## 2. Ownership Boundary

```text
Game Domain Operation
= canonical capability / state / rules / preconditions /
  transitions / postconditions / systemic quantities-rates-timing;

Execution Unit
= how an initiated process unfolds through game time and
  interacts with information, attention, Situations,
  Experience and concurrency;

Scenario execution occurrence
= one concrete manifestation in chronology;

Visual / Presentation
= how execution is represented/perceived,
  not owner of load-bearing systemic rate/timing truth.
```

A separate Execution owner may later shrink/disappear after stable truth reconciles into Domain/Visual/other owners.

## 3. When Separate Execution Planning Is Useful

Use proportionally when execution has alternative designs, persists through meaningful time, has important intermediate states, can be interrupted/reprioritized, competes for resources/capacity, overlaps other processes/Situations, emits information, changes feedback delay, carries important Experience, or has independent presentation/balance responsibility.

A trivial instantaneous Domain operation may remain inline.

## 5. Speed / Duration Ownership

Systemically meaningful movement/work speed, production/research rate, operation duration and similar values remain **Domain truth**.

Execution analyzes gameplay consequences such as decision→feedback delay, interruption window, overlap, capacity occupation, attention demand or risk accumulating while waiting.

Purely cosmetic animation/motion timing belongs to Visual. Do not move a load-bearing systemic number to Visual because animation communicates it.

## 6. Intermediate State / Information

Ask when useful: which intermediate states are game-relevant vs presentation-only; whether progress/partial evidence is visible; whether Events/Situations can alter the process; whether new information can cause replanning.

Reusable game truth discovered here should reconcile into Domain.

## 7. Interruptibility / Concurrency

Ask whether execution can pause/cancel/reassign, what interruption costs, which resources stay occupied, what can run in parallel, what competes for labor/time/space/tools/attention, and how other Active Situations modify it.

Execution happening during a Loop does not create Loop membership automatically.

## 8. Experience / Motivation / Promise / Doubt

Execution may create anticipation, plan ownership, tension through delay/exposure, mastery feedback, embodiment, information-driven Motivation change, confirmation of an Experience expectation/Promise, or Doubt when it feels decorative/arbitrary/unreadable.

Use [`Player Experience / Motivation Planning`](../player-experience-motivation-planning.md) when independently useful.

## 9. Visual / Presentation

Useful requirements include what stage/progress is perceivable, which participants/resources are visibly committed, information-source legibility, interruption/failure cues, what remains uncertain, and motion/UI/world feedback. Visual does not redefine Domain rules/rates.

## 10. Scenario / Ideas / Balance

A Scenario records one concrete Execution occurrence; it does not define every Execution Variant.

Use ordinary scoped Ideas/Variants while comparing execution designs. Balance questions may include systemic duration/rates (referenced from Domain), capacity occupation, interruption cost, feedback delay, parallelism, information timing, frequency, attention demand and waiting risk.

## 11. Do Not

- Do not make every Domain Operation an Execution Unit.
- Do not make every Scenario execution occurrence reusable.
- Do not duplicate Domain state/rules/rates.
- Do not treat animation speed as systemic speed.
- Do not create fake Situations for decisionless execution time.
- Do not assign Loop membership merely because execution occurs during a Loop.
- Do not retain a separate Execution owner after independent responsibility disappears.
